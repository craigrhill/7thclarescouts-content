# Volunteer rostering: build instructions for a fresh session

You are building a volunteer coverage rota for a small volunteer group: who
is covering which meeting or event, where the gaps are, behind a personal
sign-in code. It is a working, tested system already running for another
group. Copy it, then customise it. Do not redesign it.

The source of truth is the public repo `craigrhill/7thclarescouts-content`
on GitHub. Every file you need is listed below with a raw URL. Fetch the
files rather than retyping them from this description; the description is
here so you understand what you are copying and what to change.

## What it is

* Two static pages and one serverless function. No framework, no build for
  the pages, one small build for the function.
* Data lives in Netlify Blobs (a private key-value store that comes with any
  Netlify site). Nothing is public. The pages are useless without a code.
* Three roles, held as flags on a person and enforced by the function, never
  by the page:
  * **secretary** keeps the roster on `roster.html`: who is on it, which
    sections (teams, units, whatever the group calls them) each can cover,
    codes. The roster always keeps at least one secretary, and the page
    assumes exactly one: the role is handed on from a person's row rather
    than ticked at add time. Adding is a name (or several, comma
    separated), section chips and Add; the code appears in the row.
  * **lead** runs coverage on `rota.html` for a section: adults needed, per
    section and per meeting; anyone's ticks; marking a week as no meeting.
  * neither: sees the rota, ticks only themselves, sees only people who
    share a section with them.
* Sign-in is by personal code, `XXXX-XXXX`. The secretary sees every code on
  the roster page and can resend one; nobody else is ever given a code. A
  code returns a signed token good for 365 days. Removing a person revokes their
  token at once; "New code" cancels the old code.
* The first secretary is created with the site's admin password, on
  `roster.html`, under "First time setting this up?". After that the
  secretary issues everyone else's code.

Put the pages wherever suits the new site. They were under `lab/` in the
original because that site has a public app alongside; a fresh site can put
them at the root. Keep both pages in the same folder as `rota-lib.js` and
`rota.css`, which they reference by relative path.

## How the pieces fit

    roster.html (secretary)  \
                              ->  /.netlify/functions/rota  ->  Blobs store "rota"
    rota.html   (everyone)   /

Store keys: `secret` (the HMAC key, generated by the function on first use,
never leaves the server), `roster` (people: `id`, `name`, `sections`, `lead`,
`secretary`, `code`, `codeHash`; the code is kept so the secretary can see
it again, and the function returns it to secretaries only), `events`
(leaders-only calendar events; public ones go to the group content instead), `section/<key>` (`required`, and `slots` keyed by
slot id, each with `who` as person ids, `off`, and optional `need`).

Slot ids are made by the page, not the server: `m:YYYY-MM-DD` for a regular
meeting, `e:YYYY-MM-DD:Title` for an event. The server stores whatever ticks
it is given against those ids, so the page decides what the calendar is.

Every write is read, modify, write guarded by the document's etag and
retried on conflict. Two people saving at the same moment do not overwrite
each other. Keep that; it is why the function reads with strong consistency
and writes with `onlyIfMatch`.

## What to customise for the new group

1. **Where the public calendar lives.** The secretary can add calendar
   events. A "leaders only" one is kept in the rota store and needs nothing
   else. A public one is written back into the group's own content file, so
   it reaches the public site as well as the rota; in the original that is
   `content.json` through the GitHub contents API, guarded by the sha from
   the read the change was based on. If the new group has no such file,
   either point that write at whatever holds its calendar, or drop the
   public path and keep every event in the rota store.
2. **Where sections and events come from.** The original reads them from
   that site's public content endpoint in `loadContent()` in `rota-lib.js`,
   and `rota.html` builds the next eight weeks of meetings from each
   section's `day` (a weekday name) plus that section's events. The new
   group needs its own source. Simplest: a static `rota-config.json` next to
   the pages, shaped like this, and `loadContent()` fetches it:

       { "settings": { "sections": [
           { "key": "juniors", "name": "Juniors", "day": "Tuesday",
             "time": "6:00 to 7:00 pm", "venue": "The Hall" } ] },
         "events": [
           { "date": "2027-03-14", "endDate": "2027-03-15", "title": "Spring camp",
             "section": "juniors", "location": "Ruan" } ] }

   Section `key` must match `^[a-z0-9-]{1,32}$`; the function validates it.
   An event with no `section`, or `section: "all"`, shows for every section.
   Change the fallback in `loadContent()` too, or remove it.
3. **The admin password.** `BUILT_IN_HASH` in `rota.mjs` is the SHA-256 hex
   of the original site's admin password. Replace it with the new group's:
   `node -e "console.log(require('crypto').createHash('sha256').update('the password').digest('hex'))"`.
   Or set `ADMIN_PASSWORD` in Netlify's environment variables, scoped to
   Functions, and the hash is ignored. Never commit the password itself.
4. **Wording.** "Scouter", "section", "section lead", "group secretary" are
   in the pages' text and in the function's error messages. Search and
   replace to match the group's own words.
5. **Look.** `rota.css` carries the palette as CSS variables at the top and
   the two Google fonts are linked in each page's head. Change those; the
   layout does not care.
6. **Store name.** `STORE = "rota"` in `rota.mjs`. Only matters if the same
   site ever runs two of these.
7. **Token life.** `TOKEN_DAYS = 365` in `rota.mjs`.

## Build, test, preview

    npm install                 # esbuild and @netlify/blobs, dev only
    npm run build:function      # netlify/src/*.mjs -> netlify/functions/*.mjs
    npm run test:function       # the offline harness, expect 43 passed
    npm run serve               # http://127.0.0.1:8899, real function, memory store

The build script must include `--out-extension:.js=.mjs`. Without it esbuild
writes `.js` beside your `.mjs` and Netlify sees two functions with the same
name. The built file is self-contained: it bundles the Blobs client so it
works even from a zip drag-and-drop deploy. Never edit the built file; edit
the source and rebuild, then commit both.

The harness is the fast check. Run it after any change to `rota.mjs`. For
the pages, run the preview and walk the flow in a browser: first-time setup
on the roster page, add a person, sign in with their code on the rota page
in a private window, tick, and check the other window sees it. In the
original this was automated with Playwright against the preview; do the
same if you can, and take screenshots at 390px and 1280px.

## Deploy on Netlify

* Functions directory `netlify/functions` in `netlify.toml`. Blobs needs no
  setup; it is on for every site. No environment variables are required.
* Add `X-Robots-Tag: noindex` for the two pages in `netlify.toml`, the way
  the original does for `/lab/*`.
* If the site has a service worker, exclude the rota pages from its cache
  (the original returns early for `/lab/` in `sw.js`). Otherwise a cached
  page shows one deploy behind.
* First run: open `roster.html`, expand "First time setting this up?", enter
  a name and the admin password. That creates the secretary and shows their
  code. Everything after that happens on the roster page.
* Confirm the function is up before handing it over: `OPTIONS` on the
  function returns 204, a `GET` without a token returns 401 with
  `{"error":"Please sign in."}`. A 401 rather than a 500 proves the store is
  reachable, because the function reads or creates its secret before it
  checks anything.

## Before you say it is done

* Harness: 43 passed.
* In the preview, in two browser contexts: secretary creates a lead and a
  member; the lead signs in on the rota page and has no roster controls; the
  member signs in and can tick only themselves, sees only people who share
  a section, and sees the lead's tick; the secretary issues a new code and
  removes someone, and the removed person is signed out on reload.
* Live: the two pages return 200 with the noindex header, the stylesheet is
  served as `text/css`, and the function answers as above.
* Nothing private in the repo: no password, no codes, no names beyond what
  the group is happy to have in a public repo. If the repo is private that
  last point relaxes; the other two never do.

## Pitfalls already hit, so you do not

* `new Response("", { status: 204 })` throws under the Fetch spec; a 204 must
  have a `null` body. The original had that bug and every CORS preflight was
  a 502 until it was found.
* A local preview that serves `.css` without a `text/css` content type gets
  its stylesheet silently ignored by the browser. `serve.mjs` sets it now.
* Netlify environment variables have scopes. One set for Builds only is
  invisible to functions, and the failure looks identical to not setting
  it. If you use `ADMIN_PASSWORD`, scope it to Functions and redeploy.
* Playwright: `text=Sign in` matches a heading before a button of the same
  name. Use `getByRole("button", { name: "Sign in", exact: true })`.
* In the harness, capture a person's code and id on the line that creates
  them; later calls reassign the response variable.
